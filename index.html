GitHub Action · OpenCode agent

opencode-action —
Run the OpenCode agent in GitHub Actions

dceoy/opencode-action is a composite action that runs the AI coding agent OpenCode as a GitHub Actions job. Just write /opencode (or /oc) in an inline comment on a pull request diff and the agent starts right there — explaining the change, suggesting fixes, and editing code. It also supports generic tasks via manual dispatch and automated PR reviews in an isolated environment using the pr-review skill from pr-loop.

01Quick start — 3 steps

The minimal setup is just three things: register one secret, add one workflow file, then comment on a PR diff.

1. Register a provider secret

In your repository's Settings → Secrets and variables → Actions, register the API key for the model provider you want to use. The example below uses OpenCode's OPENCODE_API_KEY (see Models & secrets for the provider table).

2. Add a workflow

.github/workflows/opencode.yml
---
name: OpenCode
on:
  pull_request_review_comment:
    types: [created]
permissions:
  contents: read
  issues: write
  pull-requests: write
  id-token: write
jobs:
  opencode:
    if: contains(github.event.comment.body, '/oc') || contains(github.event.comment.body, '/opencode')
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1  # v7.0.1
        with:
          persist-credentials: false
      - name: Run OpenCode
        uses: dceoy/opencode-action@cda16d479232f0998a3046425dc43747f1c4c66e  # v1.1.0
        env:
          OPENCODE_API_KEY: ${{ secrets.OPENCODE_API_KEY }}
          GITHUB_TOKEN: ${{ github.token }}
        with:
          model: opencode-go/kimi-k3

In the default configuration, id-token: write is required so the workflow's OIDC token can be exchanged for an OpenCode GitHub App token. This repository's convention is to pin action references to a full commit SHA, not a tag.

3. Write an inline comment on a PR diff

PR review comment
/opencode explain this change

# The short trigger works too
/oc suggest a fix

The agent replies in that comment thread. You can change the trigger words with the mentions input (default /opencode,/oc).

02How it works

Five stages from comment to reply. Select a step to see its details.

How v2 handles credentials is the key point. In the default (OIDC) mode, GitHub credentials are not passed into OpenCode's environment, and gh runs unauthenticated. Only the launcher posts the final message as a reply to the review comment thread. To let the agent write code (git push), you need use-github-token: true plus persisted checkout credentials and a writable token.

03Three ways to use it

You can call the action directly, or use one of two reusable workflows that keep the caller small.

Basic pattern

Call it directly from a step in your own workflow with uses: dceoy/opencode-action@<SHA>. The Quick start above uses this form. Use it when you want full control over the trigger (review comment / dispatch / arbitrary event), permissions, and whether to check out.

  • When used directly via workflow_dispatch, the same inputs as workflow_call are available, and a model plus a non-empty prompt are required to run.
  • Outputs are opencode-version, runtime (v1/v2), and cache-hit.

Reusable workflow

A general-purpose bot for inline PR review comments with /opencode / /oc, manual dispatch, and arbitrary events with a fixed prompt. Review comments are accepted only when they come from an OWNER / MEMBER / COLLABORATOR and contain one of the mentions phrases (passing a model does not bypass this condition). For non-comment events, a non-empty prompt is required.

caller workflow
---
name: OpenCode
on:
  pull_request_review_comment:
    types: [created]
jobs:
  opencode:
    permissions:
      contents: read
      issues: write
      pull-requests: write
      id-token: write
      actions: read
    uses: dceoy/opencode-action/.github/workflows/opencode-bot.yml@cda16d479232f0998a3046425dc43747f1c4c66e  # v1.1.0
    with:
      model: opencode-go/kimi-k3
    secrets:
      OPENCODE_API_KEY: ${{ secrets.OPENCODE_API_KEY }}

In v2, the bot posts a reply only for pull_request_review_comment events. For workflow_dispatch and fixed-prompt runs, the launcher posts nothing.

Reusable workflow review-only

Runs automated reviews on pull_request events. It installs the external pr-review skill from dceoy/pr-loop pinned by SHA and runs it in an isolated review-only environment (see PR reviews for details). The default model is the currently free opencode/deepseek-v4.1-flash-free, so you can try it without a provider API key.

caller workflow
---
name: OpenCode review
on:
  pull_request:
    types: [opened, reopened, synchronize, ready_for_review]
jobs:
  review:
    permissions:
      contents: read
      issues: write
      pull-requests: write
      id-token: write
      actions: read
    uses: dceoy/opencode-action/.github/workflows/opencode-review.yml@cda16d479232f0998a3046425dc43747f1c4c66e  # v1.1.0

This example assumes trusted same-repository PRs. For PRs from public forks, GitHub does not pass secrets and GITHUB_TOKEN is read-only (the same applies to Dependabot PRs).

Custom providers

Providers not built into OpenCode (many are OpenAI-compatible APIs) can be defined in opencode.json at the repository root. Sakura AI Engine is the exception: it is already configured as the sakura provider in the bundled toolkit, so you can normally use sakura/* models without an opencode.json.

opencode.json
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "myprovider": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "My Provider",
      "options": {
        "baseURL": "https://api.example.com/v1",
        "apiKey": "{env:MYPROVIDER_API_KEY}"
      },
      "models": {
        "my-model": { "name": "My Model" }
      }
    }
  }
}

Treat project-side provider configuration as trusted input. Because the configuration can control baseURL and request headers, an untrusted change could send credentials to a different endpoint. Restrict workflow triggers and access to secrets appropriately. Note that in review-only runs project configuration is disabled, so custom providers cannot be used (use a built-in provider instead).

05Runtime — v1 and v2

Use the runtime input to choose the OpenCode generation. Both resolve the latest stable release published at least minimum-release-age (default 24h) ago from GitHub Releases and install that exact version. If there is no eligible release or the API fails, the run fails rather than installing an unverified fallback.

AspectOpenCode v2

You can extend the delay with minimum-release-age: 7d, or disable it with 0s. Supported units are s / m / h / d / w. Drafts, prereleases, and versions from other majors are excluded.

06Pull request reviews — Isolated review-only runs

opencode-review.yml is a read-only review design separate from normal bot runs. The review behavior itself is not bundled; it imports the pr-review skill from pr-loop at an immutable commit SHA (the former bundled /review-pr command and dedicated agent have been removed).

Restricted scope

Only PRs that are not drafts, not from bots, and opened by trusted repository collaborators are in scope. Model selection does not change this restriction.

Disposable HOME

Review-only runs use a disposable HOME under the runner's temporary directory (with separate XDG paths) and clean it up on exit. Project configuration and external skill discovery are disabled, and OpenCode is freshly installed.

Frozen evidence

Repository content is read via Git blobs (git/blobs/<SHA>), not checkout files. A symlink in the checkout cannot redirect reads to the runner's credentials.

Publishes a single COMMENT only

The upstream skill freezes base/head snapshots and publishes only findings verified against evidence as a single COMMENT review tied to the target commit. It never approves, requests changes, merges, or modifies the repository.

Restricted API adapter

GitHub operations are structured requests only, via the native pr-review-api tool. Shell expressions, arbitrary CLI flags, and file inputs are not accepted, and invalid payloads are rejected fail-closed.

Token verification

Before publishing, the App token's identity is verified with a create/delete probe of an unsubmitted pending review. The token is never written to a file or exposed in outputs.

This is not an OS sandbox. The review agent's restrictions are a boundary enforced by OpenCode tool permissions. Run it on a trusted runner and keep pull-requests: write to the minimum necessary scope. The v2 review path accepts only an empty prompt or /pr-review; free-text review focus is available only with runtime: v1 (e.g. prompt: Focus on security and performance.). Review-only v1 requires OpenCode v1.2.14 or later.

To use review-only from the direct action, you need review-only: 'true', use-bundled-toolkit: 'true' (required), the full commit SHA for pr-review-ref, and the target PR's URL and head SHA. Review-only runs do not use the OpenCode binary cache.

07Inputs reference

All of the action's inputs, filterable by text. The reusable workflows expose almost the same inputs; runs-on exists only on the reusable side.

InputDefaultDescription

Outputs: opencode-version / runtime / cache-hit.

Sakura AI Engine model sync

An optional sync workflow discovers chat-capable Sakura AI Engine models and automatically opens or updates a PR when the catalog changes. Enabling it requires the SAKURA_AI_ENGINE_API_KEY secret. PR creation uses the repository's standard GITHUB_TOKEN (contents: write / pull-requests: write); no additional token secret is needed. However, because events created by GITHUB_TOKEN do not start new workflows, this sync PR will not automatically trigger pull_request workflows.

Releases

The release workflow runs automatically on Mondays at 09:15 JST in weeks when target files have changed, and can also be run manually with major / minor / patch specified. After publishing, it updates the major version tag and opens a PR to update the SHA pins. This release → pin-update PR cycle keeps consumers' SHA pins fresh.

08Security — Token modes and trust boundaries

There are two modes for passing the GitHub token, with clearly different trade-offs.

Default

OIDC → App token exchange

use-github-token: false. Exchanges the workflow's OIDC token for an OpenCode GitHub App token (id-token: write required). In v2, neither the App token nor the OIDC credentials are passed to OpenCode itself or its child processes; the launcher holds them in memory. gh is unauthenticated.

Explicitly enabled

Use the workflow token

use-github-token: true. This is required for runs that write code (git push). However, in token mode the persisted checkout credentials are readable from OpenCode's shell, and the token is not isolated from the model. Scope it to least privilege.

  1. No unverified fallbackIf runtime resolution finds no eligible stable release or the Releases API fails, the run fails instead of installing a guessed version.
  2. Publishing only with a verified tokenThe default review-publishing path requires an OpenCode App token that has passed the identity probe. Absence or mismatch is fail-closed.
  3. Tokens are not retainedThe App token is never written to a file or included in the action's outputs. The v2 launcher holds it in memory only.
  4. Trigger trust gateAccepting a bot review comment requires both OWNER / MEMBER / COLLABORATOR authorship and a mentions match (when calling the action directly, gate this on the caller side).
  5. Permission ceiling for reusable workflowsThe callee is capped at contents: read and cannot be raised even if the caller holds stronger permissions. A separately passed GH_TOKEN is outside this ceiling.
  6. Reviews are read-only by defaultThe review-only agent is deny-by-default, allowing only skill reads, trusted reference reads, and the native API tool. Formatters and language servers are also disabled.
